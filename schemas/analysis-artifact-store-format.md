# Analysis artifacts and referenced inputs v1

Every registered analysis run, and each stage of a host workflow inside one, reserves
`.basecraft/analyses-v1/runs/RUN-ID/` beside the final primary output. No project
marker is required or created. Other analysis families retain their existing
paths until explicitly adapted. Old companion files are never migrated or removed.

Distance matrices keep the requested TSV visible; observed distance/shared-site
JSON and the native run report use the same hidden run. NJ/UPGMA, FastTree,
IQ-TREE and every disconnected forest component already share this allocation.
Their useful Newick results stay visible; alignment associations, support/style
metadata, IQ-TREE reports/logs and distance data stay hidden. Clean matrix inputs
use the same reference-first evidence as trees, and dirty matrix submissions
retain their exact generated bytes. Explicit export destinations remain caller
selected.

`store.json` identifies `basecraft.analysis-store`, schema version 1. An existing
unmarked, foreign or future namespace is refused. Managed paths reject traversal
and symlink directories. Run IDs are unique ASCII alphanumeric/hyphen components.
`pending/` owns incomplete outputs. The host stages primary and ordinary supporting
outputs here; successful no-clobber hardlink publication preserves primary/component
filenames in the working directory and puts supporting files in the hidden run.
An existing destination is an error. File/directory sync errors can leave partial
publication; sources, diagnostics and already published artifacts remain available.
There is no cross-file transaction, distributed sync lock, automatic migration or
age-based collection.

The additive public plugin parameters are:

```json
{
  "bootstrap_destination": "metadata",
  "analysis_artifacts": {
    "metadata_directory": "/absolute/output/.basecraft/analyses-v1/runs/RUN-ID",
    "working_directory": "/absolute/output",
    "run_id": "RUN-ID"
  }
}
```

The host allocates once against the actual final primary output. It injects
existing absolute directories and rejects caller-supplied allocation or explicit
`bootstrap_trees` ambiguity. `bootstrap_destination` accepts `metadata` (default)
or `working`. The distance wrapper selects `bootstrap-RUN-ID.nex`; the native
engine owns streaming, temporary files and atomic no-clobber final/partial publication.
The host never republishes/copies that collection. Successful output contracts or
validated structured recovery reports/diagnostics authorize registration. Existence
alone never authorizes adoption. A complete collection can survive a failed cache,
primary or report publication; the job remains failed and collection status/count
are recorded separately. Direct plugin callers can use an explicit absolute
`bootstrap_trees` path instead of allocation; the native engine need not know ops
or hidden-store layout.

`input.json` records schema version 1, submitted BLAKE3 hash/size, transformation,
source reference and evidence state. Clean disk sources reuse the hash established
by the verified document open plus size and timestamp; device/inode support local
alias detection, not portable identity. References are relative to their run where
possible. Matching stat metadata is a change signal, never proof of identical bytes.
No whole-input identity hash is recomputed on save-warning/UI queries. Explicit
verification, preservation and relinking check content hashes.

`canonical-fasta-v1` means the ops alignment serializer (headers/descriptions and
60-column residue lines, padding from the loaded alignment). `ungapped-fasta-v1`
means the ops ungapped serializer (row names, gap removal, 60-column lines). The
actual submitted hash is independent of the original raw-file hash. trimAl also
records its neutral-ID mapping and diagnostic log. Dirty input has no disk-source
claim: `generated` retains one exact `submitted.fasta`. A verified clean source
may be reconstructed into a disposable canonical cache on explicit tree extraction;
the cache is never substituted for missing/changed original evidence.

`identity-v1` means the submitted bytes are the source bytes unchanged. Two
generated transformations retain their payload in the run:
`blast-query-preparation-v1` (the frozen BLAST submission) and
`sequence-arrow-buffers-v1` (a sequence operation's session snapshot: residue
length as little-endian u64, residues, then the feature buffer).

A sequence-proposal run given a file reads that file and proposes edits to
the same document. Its referenced input record carries `"proposal_target":
true`. The record, source reference and hashes stay as written, the run's
generated snapshot retains the residues and features the plugin was given,
and the edited document records the run in its own history. The save guard does
not list such a record as an affected analysis, so saving the edited document
needs no evidence decision; after that save, verification reports the
referenced source as changed, which is the expected state. Every other run
that references the same file still guards it. Records without the field
behave as before.

Evidence states are `referenced`, `generated`, `preserved` and `broken`.
Before replacement, the shared Session save guard inspects known stores and
ancestor-folder stores, using metadata only. It lists direct and declared downstream
analyses. Cancel performs no replacement. Preserve-copy verifies/copies the actual
old source into affected direct runs before any replacement and publishes evidence
state before save. Candidate bytes are verified in a temporary file before
no-clobber publication. A repeated decision verifies/reuses the retained copy;
it never replaces existing retained bytes with the current source. Damaged
retained bytes are reported and left in place for recovery; descendants follow the owning ledger. If old bytes are missing
or changed, preservation is refused. Remove-analysis moves only affected hidden run
records into store trash; scientific results and user source files remain. Break-
evidence keeps records/results and explicitly marks evidence broken. Failed decisions
abort the save; partial preservation/trash decisions remain recoverable. Save As
new paths normally needs no decision and keeps references to the contributing
ledger, including bounded delegation through saved companions. Relinking a saved
copy repairs that effective owning ledger only after checking original identity.
CLI/MCP/default Rust Session saves return a structured conflict/options
without an interactive prompt; Rust callers can choose `save_with_evidence`.

Save checks return known affected analyses separately from incomplete inspection
issues. An incomplete check requires an explicit, single-use acknowledgement bound
to the live document, destination and inspected evidence. Cancel is the default;
acknowledging an incomplete check does not select a policy for known analyses.
Stale or reused decisions return a fresh check. Successful overrides retain the
inspection issues as warnings. GUI, CLI, Python and MCP use the same typed result.

The current private index consists of a checksummed source catalogue,
`analysis-input-index.json`, store summaries and one small shard per hashed source
path below `analysis-inputs`. The source shard lists the connected stores that may
own or depend on that input. Registration updates these records explicitly; there
is no older-writer reconciliation or compatibility gate. A durable dirty marker
records new direct-source paths so unrelated saves can continue. Pending dependency
changes have unknown coverage until registration succeeds. The ledger directory is
synced before the updated index can clear its marker. Index damage
never authorizes an unchecked save.

Lookup stats live indexed source paths to detect external replacement and new
hard-link aliases, then opens only the matching source shards and selected stores.
No unrelated run or input ledger is opened. Missing source paths stay uncertain.
Current stores carry an immutable identity file; discovery of the same identity
at a new location retires the absent location. Registration updates ownership and
dependency closures before releasing the relevant source/store reservations.

Saves and mutations reserve source paths, file identities and affected stores.
Conflicting operations return Busy and can retry; unrelated saves may overlap.
A catalogue lock makes selection and reservation atomic with index publication.
Direct-source updates scan outside it; ancestry updates retain it through ledger
and index publication because their pending coverage is unknown. Large ancestry
updates can therefore delay unrelated lookups until publication finishes. There is no filesystem journal or support for older record layouts.

External editors cannot be intercepted. Verification reports changed/missing
originals. Verified-original relink accepts only matching bytes and updates the
read-only source location. No startup scan/hash of a filesystem occurs. Unknown
input/reference/registry fields survive updates; future schema versions fail.
`upstream` entries reference immutable publication ID/hash/location. Bounded
verification traverses declared records and their owning evidence decisions.
Current inferred links refer to the owning run. Presentation and Save As guard
companions use their current formats; there are no older-format migration paths.

Bindings select the hidden run for a primary/component basename. The run retains
`execution.json`, a compact `run.json`, optional publication/reports and declared
artifacts. Application-state job records point to the artifact run rather than
retaining duplicate clean inputs. Optional provenance None/LocalOnly remains
separate from the minimum analysis/evidence record needed for these protections.
Complete export is explicit: it materializes the dependency closure in a new
package and provides a standard tree/alignment association when applicable.
Saved companions select this path by their evidence content as well as hidden
bindings. The entire immutable parent graph and declared upstream records are
included: export assigns new relocation identities and recomputes parent checksums,
materializes input references, and retains the original immutable JSON byte-for-byte
as checked artifacts. A checked `export-map.json` artifact maps original IDs/hashes
to export IDs. Source records remain untouched, and export verifies independently
of the original source, hidden store and saved companion. Run/binding filenames
are explicit UTF-8 JSON strings; unsupported native filenames are refused.

Host input-I/O counters cover post-open source-identity hashing, execution-scratch
reads and persistent generated-input copies. They exclude initial document loading,
mmap page faults and external-tool reads. Preservation records actual verified
copied bytes. They establish avoidance of extra host I/O, not storage-device timing
or biological reproducibility.

Species workspace routes use the same allocator and evidence lifecycle for
GMYC single/multiple/exhaustive, ASAP, PTP/mPTP, manual cuts and workspace setup.
A standalone run publishes one canonical SPART (the requested SPART/XML path,
or the output stem with `.spart`). JSON envelopes, per-fit exchange files,
mappings, fits, preparation trees and raw upstream directories remain inside
reserved runs. Adding a method to an open workspace applies typed hypotheses to
that same SPART. The GUI leaves those edits pending Save; CLI/SDK/MCP save them
through the normal guarded Session API. Useful explicitly requested display
trees remain ordinary results. Internal preparation trees remain hidden.

Species execution uses `analysis_artifacts` allocation directly, preserving
stable embedded paths rather than relocating JSON after generic staging. Public
`input_evidence` identifies the accepted raw source and exact submitted hash;
`canonical-newick-v1` denotes the tree document's Newick serializer, and
`identity-v1` denotes a frozen raw file read. Generated submissions retain one
`submitted.fasta` (the historical evidence filename is format-neutral).
Clean sources are not copied by the native wrapper. Run-local generated outputs
can be retained in place; mutable canonical workspace metadata gets an immutable
content-addressed revision. Input ledgers declare immutable upstream records for
pipelines, fitted hypotheses, attached displays and combined source workspaces.

SPART workspace metadata version 2 records its original folder as `path_base`.
Readers rebase declared path fields when the whole folder moves; authored text
and immutable historical reports are unchanged. Version 1 visible sidecars stay
readable and are never moved or deleted on passive open. A damaged binding or
missing bound workspace metadata is an error rather than a legacy fallback.
New saves and Save As use hidden metadata. Explicit complete export uses the
common dependency-closure exporter and relocates the derived workspace's input,
display and report paths into checked package artifacts, preserving the original
scientific records as immutable evidence. Historical command paths describe the
actual execution environment; exports do not claim executable scientific replay.

Explicit distance `cache` paths are handled by the shared host for matrix and
ordinary tree jobs. Computed observed-distance evidence always stays in the
allocated run. An existing ordinary cache is a candidate input: the host freezes
and verifies its bytes as `cache-input.json`, records its accepted hash/stat and
source location in `cache-input-record.json`, and declares a checked retained
auxiliary input in the publication. The native engine still validates dimensions,
model, alignment identity and overlap before reuse. A valid nonmatching cache
causes computation inside the run; the existing external file is left intact.
Malformed caches fail without replacement. Cache data is derived evidence; this
retention does not create a permanent copy of a clean original alignment.

A previously absent caller-selected cache is an intentional secondary export,
declared before execution in `cache-publication.json`. The host rejects aliases
to inputs/results/control files, symlinks, invalid parents and returned paths
outside allocation. All plugin-returned paths are checked before publication.
Supporting data is retained first; the explicit secondary is staged on its chosen
filesystem and published with no-clobber semantics before primary/component
results. A late collision or failed secondary write leaves the primary staged,
records failure and keeps hidden evidence/recovery, including any already
published bootstrap collection. Multiple publications are not a transaction.
The public result and tool log include a newly exported cache; portable provenance
uses its checked hidden evidence and destination/publication record, allowing an
explicit export outside the primary folder without unsafe relative artifacts.
Deleting that separate export does not delete the owning analysis evidence.
